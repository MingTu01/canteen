## 1. 项目定位

食堂现场 X86 触屏一体机专用程序，分**订餐终端**与**取餐终端**两种固定设备。采用「**Python Shell 全屏运行 + 隐藏管理入口**」架构：

- **运行模式**（面向员工，日常运行）：开机自启，**默认全屏无边框**，按配置的模式**固定**显示订餐或取餐界面，**运行中不可切换模式、不可随意退出**（防误操作）
- **管理模式**（管理员使用，隐藏入口触发）：连续点击窗口右上角 6 下 → 密码验证（调后端 `/api/admin/login`）→ 选择「配置模式 / 退出 / 取消」
- 一台设备 = 一种模式，不混用

### 关键特性

- **本地缓存**（核心需求）：菜品 + 菜品图片 + 菜单 + 员工头像 + 订单查询结果，断网仍可展示，**减少服务器压力**
- **SSE 实时更新**：菜品/菜单变更实时推送，一次性 ticket 认证
- **读卡器集成**：USB HID 模拟键盘 + 内置 CH372 驱动（ctypes 调 OUR_IDR.dll）
- **Python Shell 桌面壳**：PyQt5 + QWebEngineView，兼容 Win7/Win10/Win11 32/64 位
- **单实例限制**：Windows 命名 Mutex，防止端口占用导致 origin 变化使数据"丢失"
- **配置文件支持注释**：EXE 同目录的 `config.json` 支持 `//` 行注释

## 4. 本地缓存策略（核心需求）

> **用户需求**：X86 要缓存菜单、订餐、菜品、菜品图片、和所有个人头像，减少服务器压力

### 4.1 缓存范围

| 缓存对象 | 缓存策略 | Object Store | 说明 |
|----------|----------|--------------|------|
| **菜品数据** | 全量缓存 + 全清重写 | `dishes`（DB: canteen_terminal） | 含已下架菜品，供终端本地展示 |
| **菜品图片** | 全量缓存 + 孤儿清理 | `images`（DB: canteen_terminal） | Blob 存储，ObjectURL 由组件独占管理 |
| **菜单数据** | 按日期缓存 + 精确失效 | `menus`（DB: canteen_terminal） | key=`menu_${storeId}_${date}` |
| **员工头像** | **懒加载**（刷卡识别到员工时才缓存） | `avatars`（DB: canteen_terminal_avatar） | 独立 DB，30 天 TTL |
| **订单查询** | 内存缓存 + SSE 失效 | 无（内存 ref） | 不持久化，每次启动重新查询。**当前 OrderQuery.vue 未 watch `menuInvalidated`，不响应 SSE 事件（待修复）** |

### 4.2 IndexedDB Schema（db.ts）

**数据库 1**：`canteen_terminal`（DB_VERSION = 1）

| Store | key | value | 用途 |
|-------|-----|-------|------|
| `dishes` | `id`(number，keyPath) | Dish 对象 | 菜品数据 |
| `images` | `imageUrl`(string，外键) | Blob | 菜品图片 |
| `menus` | `menu_${storeId}_${date}`(string，外键) | 菜单数组 | 菜单查询结果 |

**数据库 2**：`canteen_terminal_avatar`（独立，与菜品缓存分离）

| Store | key | value | 用途 |
|-------|-----|-------|------|
| `avatars` | 头像纯路径（去掉 `?v=` 查询参数） | `{ blob: Blob, version: string, timestamp: number }` | 员工头像 |

### 4.3 菜品缓存初始化流程（initLocalCache）

```
1. 若 storeId 变化则先销毁旧缓存（destroyLocalCache）
2. 先读本地缓存实现"秒开"（dbGetAllDishes）
3. 后台异步 refreshDishes 拉取最新菜品 + 图片
4. 启动 SSE 长连接（startSse）
5. 启动 5 分钟兜底轮询（startFallbackPoll）
```

### 4.4 SSE 实时更新（startSse）

**认证安全**：不通过 URL query 传 token（会进浏览器历史/Referer/代理日志），改用**一次性 ticket**：
1. 用 Bearer token 调 `/api/sse/ticket` 获取 30s 一次性 ticket
2. 用 ticket 建立 EventSource
3. 校验后立即销毁 ticket

**监听事件**：
- `dish_changed`：菜品变更 → 全量刷新菜品
- `dish_batch_changed`：批量菜品变更 → 全量刷新菜品
- `menu_changed`：菜单变更（含日期信息）→ **精确失效指定日期菜单缓存**（不影响其他日期），通过 `menuInvalidated` ref 事件总线通知 UI 组件

**事件防抖**：500ms 内多次事件只刷新一次（`sseTriggeredRefresh`）

### 4.5 SSE 重连策略（scheduleReconnect）

指数退避 + 随机抖动：5s → 10s → 20s → 40s → 60s 封顶。
jitter 避免多终端同步重连风暴。最大 10 次重连，达到上限后降级为每 5 分钟低频重试（不永久放弃）。

### 4.6 兜底轮询（startFallbackPoll）

每 5 分钟（`FALLBACK_POLL_INTERVAL = 5 * 60 * 1000`）检查 SSE 状态，断开则全量校验并尝试重启 SSE。

### 4.7 并发控制

- `refreshDishes` 用互斥锁（`refreshInFlight`）避免 clear+put 交错
- 图片下载限并发 5（`downloadImageUrls`）

### 4.8 图片 URL 处理

支持两种源：
- `/uploads/xxx.jpg`（相对路径，拼 baseUrl）
- `https://xxx.com/xxx.jpg`（外部图床绝对 URL）

`getDishImgUrl` 优先返回本地 Blob 的 `blob:` URL（每次调用创建新 ObjectURL，调用方独占管理 revoke），未命中降级返回后端原始 URL。

### 4.9 缓存失效策略

- **菜品**：采用"全清+重写"策略（`dbClearDishesByStore`），并清理不再使用的孤儿图片 Blob（`dbClearUnusedImages`）
- **菜单**：按日期精确失效（SSE `menu_changed` 含日期信息）
- **头像**：三重校验
  1. **版本号**：URL 中的 `?v=mtime` 作为版本号，版本号变化时重新缓存
  2. **TTL**：30 天（`CACHE_TTL = 30 * 24 * 60 * 60 * 1000`），超期自动清理
  3. **路径过滤**：只缓存 `/uploads/` 路径，`data:`/`blob:` URL 直接返回

### 4.10 头像缓存降级

fetch 失败（CORS/网络）返回 `fullUrl`（带 baseUrl 的完整 URL）让 `<img>` 标签直查后端。**关键**：不能返回原始相对 url，否则终端会请求 `http://127.0.0.1:1287/uploads/...` 导致 404。

### 4.11 IndexedDB 容错

- 事务绑定 `onabort`，避免事务中止时 Promise 永久挂起（quota 超限/版本变更）
- IndexedDB 不可用时（隐私模式）所有方法 reject，调用方降级直查后端
- `dbPutImage` 检测 `QuotaExceededError`，触发全量清理后重试一次
- ObjectURL 由组件独占管理（`getDishImageBlob` 只返回 Blob），彻底消除双重所有权导致的裂图问题

### 4.12 CachedDish 结构

`id, storeId, name, price, image, category, mealTypes, status, updatedAt`

### 4.13 品牌资源缓存（branding.ts）

- **ETag + If-None-Match**：请求品牌资源（logo/食堂名等）携带上次 ETag，服务端返回 304 Not Modified 时复用本地缓存，减少传输
- **absolutizeUrl**：将品牌资源中的相对 URL 转为绝对 URL（拼 baseUrl），避免终端 origin（`http://127.0.0.1:1287`）下相对路径 404
- 与 IndexedDB 菜品缓存分离：branding 存内存，随绑定状态加载/清理（解绑时 `clearBranding`）

## 5. 管理入口与配置程序

### 5.1 隐藏管理入口（AdminEntryZone.vue）

运行模式下界面无任何管理按钮，**连续点击窗口右上角 6 下**（2 秒内）触发：

```
连续点击右上角 6 下（120×120px 透明热区）
       ↓
弹出密码输入框（居中模态）
       ↓
调用后端 /api/admin/login 验证管理员账号密码（BCrypt，非本地 SHA256）
       ↓
验证通过 → 弹出三按钮操作菜单
       ↓
┌──────────────┬──────────────┬──────────────┐
│   配置模式    │     退出      │     取消      │
│ 跳转 /settings│ 关闭整个应用   │ 返回运行模式   │
└──────────────┴──────────────┴──────────────┘
```

**关键参数**：
- 热区：右上角 `120×120px` 透明点击区（`HOT_ZONE_SIZE = 120`，`position: fixed; top: 0; right: 0`，z-index: 100）
- 点击计数：`CLICK_THRESHOLD = 6` 次，`CLICK_WINDOW_MS = 2000` 毫秒内
- 超时重置：`CLICK_WINDOW_MS + 200`（2.2 秒）后清零计数

**弹窗遮罩行为**：
- 管理员登录弹窗和操作菜单弹窗的 `.modal__overlay` **均没有 `@click.self` 关闭逻辑**
- **点击遮罩不会关闭弹窗**，只能通过右上角 X 按钮或操作按钮关闭（避免多点一下就取消的问题）

**三个操作选项**：
1. **配置模式**（`enterConfigMode`）：跳转 `/settings`（窗口模式由配置页保存时触发 Python 信号处理）
2. **退出**（`onQuitApp`）：调用 `quitApp()` 退出整个应用
3. **取消**（`closeActionModal`）：关闭弹窗回到运行模式

### 5.2 配置程序（Settings.vue）

首次启动 / 未配置时直接进入配置界面；管理员通过隐藏入口触发后亦可再次进入。

**未绑定状态**：绑定表单
- 服务器域名（留空=同源开发模式，可省略端口自动探测）
- 管理员账号 + 密码
- 食堂安全码（8 位，向超管索取）
- 设备标识（可选）
- 运行模式选择（订餐机/取餐机）
- 「测试并绑定」：调 `POST /api/terminal/bind` 双重校验（管理员账号密码 + 食堂安全码，storeId 一致）→ 签发终端 token（role=3，storeId 锁定）

**已绑定状态**：
- 绑定信息卡（服务器、食堂、设备标识、绑定时间）
- 运行模式切换（订餐机/取餐机，立即生效）
- **终端运行设置卡**（仅 Python Shell 环境显示，`v-if="isPythonShell"`）
- 解绑按钮（需管理员密码二次校验）

### 5.3 终端运行设置（仅 Python Shell）

| 设置项 | 范围 | 默认值 | 说明 |
|--------|------|--------|------|
| 窗口模式 | 全屏无边框 / 窗口模式(1280×800) | fullscreen | 分段切换 |
| 读卡防抖间隔 | 0.5 ~ 10，step 0.5 | 2.0 | 秒 |
| 无操作返回待机时间 | 0 ~ 3600，step 10 | 30 | 秒，0=永不 |

**保存时机**：点击"进入运行模式"时自动保存（`goRun` → `saveRuntimeConfig`），**无独立保存按钮**。

**窗口/全屏切换生效时机**：
- `setRuntimeConfig` POST `/__api__/set_config` → Python `write_config` → emit `config_updated` 信号 → main.py `on_config_updated` 立即调用 `switch_to_fullscreen_mode` / `switch_to_config_mode`
- **Python Shell 模式下立即生效**（无需重启）；shellApi.ts 中"需重启"注释已过时（待清理）

### 5.4 后端端口自动探测

用户输入不带端口时，并行探测常见端口（http: 8080/80/8443/8888/9090/3000/5000/81/82/83/8081/8082/9000；https: 443/8443/8080/9080/9000），2 秒超时，no-cors 模式只检测 TCP 连通性。

### 5.5 解绑

调用 `/admin/login` 验证管理员密码，通过后 `clearConfig` + `clearBranding` + `destroyLocalCache`（停止 SSE/轮询，避免解绑后继续发请求）。

### 5.6 预设服务器地址预填

从 shell config.json 读取 `server_url` 自动填入表单（仅未绑定时）。

## 9. 鉴权与数据隔离

- **终端 token**：role=3，storeId 锁定（绑定签发，默认 365 天过期）
- **刷卡识别**：`GET /api/terminal/employee/{cardNo}` 从 token 取 storeId 查本店员工，**不签发员工 token**，门店隔离不被破坏
- **菜单**：`GET /api/menu/store/{storeId}/date/{date}`
- **下单**：`POST /api/order`（body 含 storeId/employeeId/date/mealType/items）
- **取餐扫码**：`POST /api/order/pickup {pickupCode}`
- **完成取餐**：`PUT /api/order/{id}/complete`
- **取消**：`PUT /api/order/{id}/cancel`
- **跨店访问**：role=3 token 锁 storeId，后端 `SecurityContext` 校验

### token 滚动续期

绑定超过 30 天（`TOKEN_REFRESH_THRESHOLD_DAYS`）时异步用旧 token 换新 token，避免接近 365 天过期失绑。

### 401/403 处理

token 失效或门店权限变更时，清除本地绑定 + branding + IndexedDB/SSE 缓存，跳转 `#/settings`，5 秒冷却防重入。

## 10. 读卡器集成

### 10.1 统一三种读卡器输入来源（useCardReader.ts）

1. **Python Shell**：ctypes 调 OUR_IDR.dll + IDUSB.DLL（广州荣士电子），通过 `window.__onCardRead` 推送卡号
2. **Tauri 后端**：Rust FFI 调 OUR_IDR.dll + IDUSB.DLL，发送 `card-read` 事件
3. **USB HID 键盘模拟读卡器**：keydown 监听，Enter 结束输入（降级方案）

### 10.2 Python Shell 集成

- 设置全局 `window.__onCardRead = (cardNo) => notifyHandlers(cardNo)`
- Python 端 `card_reader.py` 读到卡号 → main.py `push_card_to_frontend` → `page.runJavaScript("window.__onCardRead('xxx')")` → 触发所有注册的 handler
- 全局只初始化一次（`pythonBridgeReady` 标志）

### 10.3 USB HID 键盘降级

- 单字符缓冲，80ms 超时（`CARD_INPUT_TIMEOUT = 80`，读卡器单字符间隔通常 <50ms）
- Enter 键结束输入，触发 handler
- 输入框焦点时不拦截键盘（避免影响表单输入）

详细架构见 [05-PythonShell.md](file:///d:/文档/enterprise-canteen/enterprise-canteen/docs/05-PythonShell.md)。

## 11. 扫码取餐流程

> **实现状态**：摄像头扫码取餐（`getUserMedia` + `jsQR`）**当前未实现**。取餐终端仅支持**刷卡**和**扫码枪**（USB HID 键盘模拟，全局键盘监听捕获，回车结束 = 一个输入）。以下摄像头方案为原设计，留作后续实现参考。

取餐终端待机页入口（当前实现）：
- **刷卡取餐**：全局键盘监听 → cardNo
- **扫码枪取餐**：USB HID 扫码枪扫描员工身份二维码 → 解析 JSON → 取 cardNo（与刷卡共用键盘监听通道）

> 原设计的摄像头扫码入口：摄像头扫员工身份二维码 → 解析 JSON → 取 cardNo

两者拿到 cardNo 后流程统一：
```
拿到 cardNo
   ↓
GET /api/terminal/employee/{cardNo}  (终端 token,storeId 锁定)
   ↓
命中本店员工 → /pickup/verify(验证中,查今日订单)
   ↓
/pickup/info(取餐信息页,30秒倒计时)
   ↓
点「取餐完成」→ PUT /api/order/{id}/complete → 回待机
```

### 二维码内容（与 H5 一致）

```json
{
  "cardNo": "CARD001",
  "storeId": 1,
  "employeeId": 1,
  "name": "张明",
  "expire": 1800000000000,
  "sign": "HMAC-SHA256 前16位"
}
```

### 终端扫码校验
- 用 `jsQR` 解码摄像头帧 → 解析 JSON
- **建议简化方案**：终端扫码只取 `cardNo`，直接调 `/terminal/employee/{cardNo}`（后端已按 token 的 storeId 隔离），签名校验由后端完成。终端无需密钥，更安全
- 校验 `expire` 未过期
- 二维码非本店员工 / 已过期 / 签名错误 → 提示「无效二维码」回待机

## 12. 自动回待机机制

- 全局活动监听（触摸/鼠标/键盘），有活动重置计时器
- 计时器归零 → 跳对应模式的待机页（`/order` 或 `/pickup`），清空当前员工/订单状态
- 默认 30 秒（可配置，`idle_timeout`，0=永不）
- 取餐信息页的 30 秒倒计时与此独立（取餐信息页本身就有 30 秒返回逻辑）

## 16. 已确认决策

1. **管理入口解锁方式**：连续点击窗口右上角 6 下（2 秒内）→ 弹管理员密码框（调后端验证）→ 验证通过显示三按钮菜单
2. **默认运行模式**：全屏无边框，统一为运行模式 + 隐藏管理入口
3. **读卡器**：全部 USB HID（模拟键盘）+ Python Shell ctypes 调 DLL；统一全局键盘监听器捕获，回车结束 = 一个卡号
4. **扫码取餐**：摄像头扫员工身份二维码，扫码等同刷卡，拿到 cardNo 后走 `/pickup/verify`
5. **无操作自动回待机**：默认 30 秒（可配置）
6. **开机自启 + 不可退出**：Python Shell 全屏无边框锁定 + 系统侧配置自启
7. **分辨率**：17 寸触摸屏，1280×1024 基准（等比缩放适配其他分辨率）
8. **桌面壳**：采用 Python + PyQt5 + QWebEngineView（代码保留 Tauri 兼容分支作为 fallback，兼容 Win7/Win7 32 位）
9. **缓存策略**：菜品/菜单/菜品图片全量缓存；员工头像懒加载（刷卡识别时缓存）。断网仍可展示，减少服务器压力
10. **弹窗遮罩**：管理员登录弹窗和操作菜单弹窗点击遮罩**不关闭**（避免多点一下就取消）

## 17. 安全边界

| 边界 | 策略 |
|------|------|
| token 存储 | localStorage（`terminal_config_v2`），role=3，storeId 锁定 |
| token 提取 | Authorization Bearer |
| SSE 认证 | 一次性 ticket（30s，一次性消费），不通过 URL query 传 token |
| 门店隔离 | token 锁 storeId，后端 checkStoreAccess 校验，刷卡不签发员工 token |
| 管理入口 | 6 次点击 + 后端密码验证（BCrypt），非本地 SHA256 |
| 弹窗关闭 | 管理员弹窗点击遮罩不关闭，仅按钮关闭；**解绑弹窗遮罩当前可关闭**（与 AdminEntryZone 策略不一致，待评估是否统一） |
| 读卡防抖 | 默认 2 秒（可配置），避免重复触发 |
| 缓存清理 | 解绑时调 `destroyLocalCache`（停 SSE/轮询，**不清 IndexedDB**）；401/403 时调 `purgeLocalCache`（清 IndexedDB + 停 SSE）并跳设置页 |
| token 续期 | 30 天阈值自动滚动续期，避免 365 天过期失绑 |
| 单实例 | Windows Mutex 防止多开导致数据丢失 |
| 配置文件 | config.json 支持 `//` 注释（Python 解析） |

## 18. 全局错误兜底（main.ts）

三层捕获，避免单点异常导致终端白屏/卡死：
- `app.config.errorHandler`：捕获 Vue 组件渲染/生命周期错误
- `window.addEventListener('error', ...)`：捕获同步运行时错误（脚本异常、资源加载失败）
- `window.addEventListener('unhandledrejection', ...)`：捕获未处理的 Promise rejection

捕获后统一记录日志，防止单点异常导致整个终端静默失败。
