## 2. 为什么改（背景，理解后可跳过）

原流程是两次独立 HTTP 请求：

1. `GET /order/employee/{id}` —— 拉订单，决定菜品能否显示
2. `PUT /order/{id}/complete` —— 核销

两次请求之间隔着 **约 1.2 秒的「验证中」动画 + 路由跳转 + 组件挂载**。期间任一环节出问题：

- **网络抖动 / 交换机重启 / 后端重启**：菜品照常显示，核销请求根本没发出去
- **后端可读不可写**（连接池耗尽、主库写阻塞、磁盘满、行锁竞争）：读成功、写 500
- 核销是**非阻塞**发起的，失败只在控制台留一行日志，**界面完全无感知**

而核销有硬性时间窗（`OrderService.checkPickupTimeWindow`）：

```java
if (!order.getDate().equals(today))  throw new BusinessException("仅支持核销当日订单");
if (!isWithinDiningTime(...))        throw new BusinessException("未到用餐时间,...");
```

外加 `OrderStatusScheduler` **每 60 秒**扫一次，把「时段已过且未核销」的订单打成 `status=4`（未就餐）。
**窗口一旦错过就是永久丢失，无法事后补核销。** 表现为：订单统计与结算失真、同一人可反复取餐。

合并成一个事务后，语义变为：**能显示菜品 ⟺ 已核销成功**。

方法内部四步逻辑：

1. 校验员工存在（不存在 → `卡号不存在`）→ `SecurityContext.checkStoreAccess(employee.getStoreId())` 校验门店归属
2. `diningTimeSlotService.getCurrentMealType(storeId, now)` 判定当前餐次（`null` → `未到用餐时间,请在就餐时段内取餐`）。**餐次由服务端判定**，避免「午餐时段核销早餐订单」
3. 在该员工今日该餐次的订单中找 `status=1` 的目标；记录「该餐次是否下过单」以区分提示文案
4. 原子更新 `WHERE id=? AND status=1 SET status=2`（`rows==0` → `订单状态已变更`），再填充 `employeeName` / `cardNo` / `departmentName` 后返回

> 方法带 `@Transactional`。菜品明细 `items` 由 `getOrdersByEmployee` 批量填充，无二次查询。

## 4. 接口契约

```
POST /api/terminal/pickup
```

| 项 | 值 |
|---|---|
| 鉴权 | 终端 JWT（`role=3`），与 `/api/terminal/*` 其他端点一致；`/bind` 是唯一免鉴权端点 |
| 请求头 | `Content-Type: application/json`；终端 token 按现有方式携带 |
| 请求体 | `{ "employeeId": 123 }`（终端已完成身份识别，只传员工 ID） |
| 成功响应 | `ApiResponse<Order>`，`code=200`，`data` 为**已核销**的订单 |

成功响应 `data` 关键字段：

| 字段 | 说明 |
|---|---|
| `id` / `mealType` / `date` / `totalAmount` / `orderSource` | 订单基础信息 |
| `status` | 恒为 `2`（已完成） |
| `employeeName` / `cardNo` / `departmentName` | 展示用，服务端填充 |
| `items[]` | 菜品明细（`dishName` / `price` / `quantity` / `dishImage` / `spiceLevel`） |

失败响应（`code` + HTTP 状态由 `GlobalExceptionHandler` 统一映射，`message` 为中文原文）：

| 场景 | message |
|---|---|
| 员工不存在 | `卡号不存在` |
| 不在就餐时段 | `未到用餐时间,请在就餐时段内取餐` |
| 该餐次已取过 | `{姓名}{餐次}已取餐`（多见于上次核销成功但响应丢失） |
| 该餐次没下单 | `{姓名}{餐次}未订餐` |
| 并发状态变更 | `订单状态已变更` |
| 参数缺失 | `员工 ID 不能为空` |
| 非终端 token / 未绑定门店 | `仅终端设备可取餐核销` / `终端未绑定食堂`（HTTP 403） |

### 8.2 接口连通性（核心）

用**终端 token**（`role=3`）调用，`employeeId` 换成实际存在、当前餐次有待取餐订单的员工：

```bash
curl -X POST http://localhost:18082/api/terminal/pickup \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <终端token>" \
  -d '{"employeeId": 123}'
```

预期：`code=200`，`data.status=2`，`data.items` 有菜品。

### 8.3 数据库核对

```sql
-- 调用前应为 1(待取餐)，调用后应为 2(已完成)
SELECT id, status, date, meal_type FROM `order` WHERE id = <订单id>;
```

### 8.4 边界用例

| 用例 | 预期 |
|---|---|
| 同一员工**连续调用两次** | 第一次 200；第二次 `{姓名}{餐次}已取餐`，且订单**不会**被重复核销 |
| 非就餐时段调用 | `未到用餐时间,请在就餐时段内取餐` |
| 用 admin token（role≠3）调用 | HTTP 403 `仅终端设备可取餐核销` |
| 不存在的 employeeId | `卡号不存在` |

## 10. 已知限制 / 注意事项

1. **接口幂等性依赖 `WHERE status=1` 原子更新**，不依赖前端去重。重复调用不会重复核销，但会返回业务错误。
2. **事务边界**：`pickupForEmployee` 带 `@Transactional`，核销与订单查询在同一事务。若后续有人往方法里加远程调用（如微信通知），注意不要拉长事务持锁时间。
3. `mealTypeName` 使用 `MealType.fromCode(...).getChineseName()`，未匹配时返回空串，保证提示文案不出现 `null`。
4. 本次**未做前端/后端联调实测**（本机无法启动完整环境），仅完成静态编译验证与契约核对 —— 第 8 节的验证步骤请勿跳过。

## 11. 上一手的环境事实（供参考）

- 本机 **无 Maven**。编译验证方式：用本机 JDK 25，拼接 `~/.m2/repository` 下全部依赖 jar 为 classpath，直接 `javac` 编译两个改动文件 —— **退出码 0，通过**。
- **坑**：JDK 22+ 默认关闭注解处理，直接 `javac` 会因 Lombok 失效而报 `cannot find symbol: log` 等假错误。需加 `-proc:full` 参数，Lombok 才会正常注入。
- 上述编译验证仅证明**语法与依赖无误**，不代表运行时行为已验证。
