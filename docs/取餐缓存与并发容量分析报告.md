# X86 取餐缓存与并发容量分析报告

> 日期:2026-08-15
> 结论适用版本:后端 V0.0.51 / 终端 V1.0.32
> 场景:8 个食堂 × 每店 150 人,极端同时排队取餐;云服务器选型(腾讯云,极致性价比)

---

## 一、X86 本地缓存取餐:有没有必要做?

**结论:订单离线缓存 / 离线核销队列没必要做;员工缓存(已实现)保留即可。**

| 项目 | 现状 | 判断 | 理由 |
|---|---|---|---|
| 员工缓存(IndexedDB,24h 轮询刷新) | 已实现 | **保留** | 刷卡识别毫秒级、0 网络请求,已解决"刷卡慢"的主要痛点 |
| 订单本地缓存 | 未实现 | **不做** | 订单状态实时变化(H5 下单/取消/管理员标记未就餐),缓存订单会引入"拿旧状态核销"的一致性风险,收益接近 0 |
| 离线核销队列(断网时本地记账、恢复后上传) | 未实现 | **不做** | 核销必须以服务端 DB 为唯一事实源;离线核销需处理冲突合并、幂等重放、时钟漂移,复杂度远超收益 |

理由展开:

1. 取餐慢的根因已查明并解决(员工识别走本地缓存),网络正常时全链路 <1s,瓶颈在"人走过去拿餐"而不是网络。
2. 云服务器可用性 99.9%+(月停机 <45 分钟),极端断网期间可暂停取餐或由管理后台事后手动补标记,足够兜底。
3. 引入离线核销 = 引入分布式一致性问题,对 8 店 1200 人的规模是典型的过度设计。

## 二、网络波动会不会导致"订单已验证但后台仍显示未取餐"?

### 2.1 反向不一致(终端显示成功、后台未取餐)——架构上不可能

- 终端只凭服务端 **2xx 响应**判定成功(`PickupInfo.vue` completePickup);
- 服务端 `completeOrder` 是 `@Transactional` + 原子更新:

```sql
UPDATE `order` SET status = 2 WHERE id = ? AND status = 1
```

  事务提交成功才返回 2xx。因此"终端看到成功 ⇒ DB 必然已更新",不存在半个状态。
- 影响行数为 0 时抛"订单状态已变更"(HTTP 400),即订单已被核销/取消,不会二次扣减。

### 2.2 正向误报(终端显示失败、后台其实已取餐)——修复前存在,已修复

风险场景:请求到达服务端、DB 已更新为"已取餐",但响应包在网络中丢失 → 终端误报失败 → 操作员重刷提示"订单状态已变更"→ 困惑。数据没丢,但体验差。

**V1.0.32 修复内容**(全部在终端侧,后端零改动):

1. **自动重试**:核销请求共 3 次尝试(首试 + 重试 2 次,间隔 0.8s / 1.6s 递增);仅对网络类错误(无响应/超时/5xx)重试,4xx 业务拒绝直接跳出不重试;单次尝试超时 8s(默认 15s),避免断网时页面久卡"处理中"。
2. **失败兜底回查**:全部尝试失败后自动回查订单真实状态,若已是"已完成"(status=2)直接按成功返回待机页,彻底消除误报。
3. **错误文案区分**:
   - 回查仍为"待取餐"(status=1)且无服务端错误信息 → 提示"取餐完成失败(网络异常),订单状态未变更,请重试",告知操作员数据安全;
   - 4xx 业务拒绝(如未到用餐时间)→ 展示服务端原文。
4. **重试安全前提**:后端 `WHERE status=1` 原子更新天然幂等,重复提交无副作用。

修改文件:`terminal/src/views/PickupInfo.vue`(`completePickup` / `fetchOrderStatus`)。

## 三、极端并发计算:8 店 × 150 人同时排队,8 人同毫秒刷卡

**结论:完全没问题,压力不到服务器容量的 1%。**

### 3.1 单人取餐链路开销

| 步骤 | 开销 |
|---|---|
| 识别员工 | 本地 IndexedDB 缓存命中,**0 网络请求** |
| 查订单 | 1 次 HTTP,1~2 条 SQL(主键/索引查询) |
| 核销 | 1 次 HTTP,4 条 SQL(Controller 查单 + Service 查单 + 时段表 + 原子 UPDATE) |

### 3.2 极端突发(8 人同毫秒)

- 8 并发 × ~6 条 SQL = 48 条 SQL,全部为主键点查;
- InnoDB 行级锁,**不同订单之间零锁冲突**;
- 单条 SQL <1ms → 整个突发 <100ms 消化完毕;
- Tomcat 默认 200 线程、HikariCP 默认 10 连接 > 8 并发,**连接池都不用调**。

### 3.3 同一订单并发核销(同一人扫码 + 刷卡同时到)

原子 `UPDATE ... WHERE status=1` 保证只有一方成功,另一方收到 400"订单状态已变更"——正是幂等设计的预期行为,无超发风险。

### 3.4 实际节奏与总量

- 取餐由人决定,每人刷卡 → 看屏 → 完成约 5~10 秒;
- 单店 1 台终端:150 人约 15~25 分钟清完;想更快就加终端,每店 2 台 = 16 并发依然毫无压力;
- 叠加午高峰 H5 下单(假设 200 人同时在线,实际 QPS 约 10~20)+ 管理后台数人同时使用;
- **总峰值 < 50 req/s**,而 2 核 4G 跑这套简单 CRUD 单机能力 1000+ req/s,**余量 20 倍以上**。

## 四、腾讯云服务器推荐(极致性价比)

**推荐:轻量应用服务器 2核4G 6M 带宽(70G SSD,600G/月流量),all-in-one 部署。**

### 4.1 内存预算(4G 够用且有余量)

| 组件 | 内存 |
|---|---|
| OS(Linux) | ~0.4G |
| MySQL 8(buffer pool 512M) | ~0.8G |
| Spring Boot(-Xmx1g) | ~1.3G |
| Redis(限 128M)+ Nginx | ~0.2G |
| **合计** | **~2.7G / 4G** |

### 4.2 带宽与流量

- X86 终端图片已全量本地缓存,运行时只有 JSON API(单次 <10KB);
- H5 首载约 1MB 且强缓存(version.json 自动刷新机制);
- 6M 峰值带宽 + 600G/月流量远超需求(估算月用量 <20G)。

### 4.3 磁盘

订单月增约 7 万行 + 图片 <2G,70G SSD 可用数年。

### 4.4 当前活动价格(2026-08,以官网为准)

| 方案 | 配置 | 价格 | 说明 |
|---|---|---|---|
| **首选** | 轻量 2核4G 6M / **3 年** | **528 元(约 14.7 元/月)** | 产品首单专区,折合 176 元/年,长期最省 |
| 备选 | 轻量 2核4G 5~6M / 1 年 | 188~199 元 | 部分套餐支持同价续费 1 次,适合先试一年 |
| 极限薅羊毛 | 轻量 4核4G 3M / 1 年 | 38 元(秒杀) | 个人首单 + 限时抢;带宽仅 3M、40G 盘、续费贵,**不推荐生产** |

### 4.5 明确不选的配置及理由

- **2核2G**:JVM + MySQL + Redis 挤 2G 内存,易 OOM,高峰无余量;
- **4核8G**:负载 <1% CPU,纯浪费;
- **独立云数据库 MySQL**:每月加 30~80 元,当前数据量用快照 + 每日 mysqldump 备份足够,省下这笔。

### 4.6 数据安全配套(0 元)

- 轻量服务器自带 2 个免费快照位:设每日自动快照;
- 服务器内 cron 每日 mysqldump;
- 每月手动下载一份备份到本地/NAS 异地保存;
- 域名(如 canteen.908521.xyz)配腾讯免费 DV 证书。

### 4.7 部署形态

一台机器 Docker 跑 backend + MySQL + Redis;Nginx 托管 h5 / admin-web 静态资源并反代 `/api`——与现有 Docker 部署结构一致,直接上云。
