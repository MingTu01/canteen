## 1. 项目定位

集团级企业智慧食堂预定餐系统的统一后端 API 服务，承载多门店数据隔离、多端鉴权（管理后台 / H5 订餐端 / X86 终端）、订单全生命周期、库存采购、日终对账、报表统计、备份恢复等全部业务能力。

- **多租户隔离**：所有业务表通过 `store_id` 字段实现行级数据隔离，门店管理员只能管理本店，超级管理员可跨店。
- **统一鉴权**：JWT（HttpOnly Cookie）+ 角色权限（7 类角色）+ 门店访问拦截器三层防护。
- **实时推送**：SSE 长连接向终端推送菜品/菜单变更，一次性 ticket 认证避免 token 泄漏。
- **可观测**：操作日志切面、登录限流、健康检查、版本管理。

## 3. 安全模型（核心）

### 3.1 JWT Token 结构

签名算法：HS256/HS512（基于 `jwt.secret` 注入的 SecretKey Bean）。
统一 claims：`id`、`username/name`、`storeId`、`role`、`jti`(UUID)、`iat`、`exp`。

**三种 token 类型**：

| 类型 | claims | 过期 | 用途 |
|------|--------|------|------|
| 管理员 token | `id`/`username`/`name`/`storeId`/`role`(1/2/4/5/6) | `jwt.expiration`（默认 24h） | 管理后台 |
| 员工 token | `id`/`cardNo`/`name`/`storeId`/`departmentId`/`balance`/`role=0` | 同上 | H5 订餐端 |
| 终端 token | `storeId`/`storeName`/`role=3`/`deviceLabel`（**无 id**） | `jwt.terminal-expiration`（默认 30 天，终端绑定超 15 天自动滚动续期） | X86 终端 |

**二维码签名**（取餐扫码用）：HMAC-SHA256，内容 `cardNo|storeId|employeeId|expire`，hex 前 16 位；7 天有效；`verifyQrcodeSign` 使用 `MessageDigest.isEqual` 常量时间比较防时序攻击。

### 3.2 角色体系

| role | 常量 | 名称 | 主要权限范围 |
|------|------|------|--------------|
| 0 | `ROLE_EMPLOYEE` | 员工 | 只能操作自己订单/充值记录/反馈 |
| 1 | `ROLE_SUPER_ADMIN` | 超级管理员 | 跨门店；创建/删除管理员、门店；切换管理食堂 |
| 2 | `ROLE_STORE_ADMIN` | 门店管理员 | 仅本店；管理员工/菜品/订单/充值 |
| 3 | （终端，无常量） | 终端 | storeId 锁定；无 id；只能访问门店公开数据 |
| 4 | `ROLE_FINANCE` | 财务 | 报表 + 充值（canViewFinance/canSettle） |
| 5 | `ROLE_CHEF` | 厨师长 | 菜品 + 采购（canManageDish/canManageProcurement） |
| 6 | `ROLE_STORE_MANAGER` | 店长 | 全店管理（不可删数据） |

**权限判定辅助方法**（`SecurityContext`）：
- `hasAdminLevel()` — 非 0 非 3 且在 1~6 之间
- `canManageSystem()` — 仅 role=1（超管）
- `canViewFinance()` — 1/2/4/6
- `canManageDish()` — 1/2/5/6
- `canManageProcurement()` — 1/2/5/6
- `canSettle()` — 1/2/4/6
- `checkStoreAdminOrAbove()` — role=1/2/6（超管/门店管理员/店长）
- `hasAnyRole(roles...)` — 任意角色命中即放行
- `checkStoreAccess(targetStoreId)` — 超管放行；其他角色要求 `currentStoreId == targetStoreId`，**fail-closed**（role=null 抛异常，不静默放行）
- `checkSuperAdmin()` / `checkSuperAdmin(message)` — 仅超管，否则抛 SecurityException（支持自定义消息）
- `checkOrderOwnerOrAdmin(targetEmployeeId)` — 员工仅能操作本人；其他角色放行（由 checkStoreAccess 把关）

### 3.3 白名单（WhitelistMatcher）

**精确匹配**（无需 token）：
- `/api/admin/login`、`/api/employee/login`、`/api/employee/phone-login`
- `/api/terminal/bind`
- `/api/store/public-list`
- `/api/system/health`、`/api/system/version`、`/api/system/time`
- `/api/auth/logout`
- `/api/test/employees`
- `/api/sse/subscribe`（用一次性 ticket 认证）

**前缀匹配**：`/actuator`、`/h2-console`、`/uploads/`（静态图片资源）

**公开品牌接口正则**：`^/api/store/\d+/branding$`（GET 免登录，H5/terminal 获取品牌信息）

CORS 预检 OPTIONS 直接放行。

**CORS 允许 origin 白名单**（`WebConfig`）：
- `http://localhost:*` / `http://127.0.0.1:*`（本地开发）
- `http://tauri.localhost`（**遗留配置**：早期 Tauri 客户端使用，现已切换到 Python Shell 方案，可考虑清理）
- 实际部署时由 nginx 在前端响应中追加 CORS 头

### 3.4 门店数据隔离（StoreAccessInterceptor）

注册到 `/api/**`（排除白名单），核心逻辑：
1. OPTIONS 直接放行
2. 从路径提取 storeId：`/store/{数字}` 或 `/stores/{数字}`；查询参数 `storeId`/`store_id` 兜底
3. 无 storeId 参数则放行给 Controller 内显式 `checkStoreAccess` 校验
4. **终端（role=3）**：必须 `token.storeId == targetStoreId`，否则抛 403
5. 其他角色调用 `SecurityContext.checkStoreAccess(targetStoreId)`，失败抛 SecurityException 由 GlobalExceptionHandler 转 403

### 3.5 登录限流（LoginRateLimiter）

- 默认 **10 次失败 → 锁定 5 分钟**（内网部署放宽）
- 配置项（从 `sys_config` 表读取，60 秒刷新）：
  - `login_rate_limit_max_fail`（默认 10）
  - `login_rate_limit_lock_minutes`（默认 5）
- 内存 `ConcurrentHashMap`（单实例；多实例需替换 Redis 版本）
- 三方法：`checkLocked(key)` 抛 403 / `recordFail(key)` / `recordSuccess(key)` 清空失败计数
- 应用于：管理员登录、员工卡号登录、员工手机号登录、终端绑定、取餐码核销、改密
- **禁止使用 `Thread.sleep()` 在 Servlet 线程中阻塞**，统一走 LoginRateLimiter

### 3.6 密码策略（BCrypt + PasswordFreshnessValidator）

- **加密**：BCrypt（strength=10）
- **最小长度**：8 位（前后端一致）
- `passwordUpdatedAt` 字段：V10 迁移加入 employee/admin 表；改密时同步更新
- **PasswordFreshnessValidator**：`iat + 5s < passwordUpdatedAt` 则拒绝（5 秒宽限期防时钟漂移）
  - 仅对 role=0（员工）和 1/2/4/5/6（管理员）校验
  - role=3（终端）跳过
- **软删除/禁用后 token 失效**：`is_deleted=1` 或 `status!=1` 返回"账号已失效"
- **JwtAuthenticationFilter 主流程**：白名单放行 → 多源取 token（Authorization Bearer 优先，Cookie 兜底） → 校验签名 → 黑名单校验 → 密码新鲜度校验 → UserContextBinder 按角色写 request attribute

### 3.7 Token 黑名单（TokenBlacklistService）

- 存储：数据库表 `token_blacklist`（按 jti 维度，单/多实例皆可）
- 注销时：`UPDATE/INSERT token_jiti + expires_at`（自然过期时间）
- 校验：`SELECT COUNT(*) WHERE token_jti = ?`
- **失败关闭**：查询异常视为已注销，拒绝请求（避免 DB 故障时已注销 token 复活）
- 定时清理：`@Scheduled(fixedDelay=300_000, initialDelay=60_000)` 每 5 分钟删除已过期条目

### 3.8 Cookie 设置（AuthCookieUtil）

- 名称：`auth_token`
- HttpOnly：true（防 XSS 窃取）
- Secure：跟随 `request.isSecure()`（prod 强制 HTTPS）
- Path：`/`
- SameSite：`Strict`（防 CSRF）
- maxAge：与 `jwt.expiration` 对齐（默认 24h）
- **TokenExtractor**：`Authorization: Bearer` 优先 → Cookie 兜底；**已移除 `?token=xxx` 支持**（防 URL query 进入历史/Referer/代理日志）；SSE 改用一次性 ticket 机制

### 3.9 文件上传安全（FileController）

- 最大 5MB（防御性上限，前端已 canvas 压缩到 300x300 / JPEG 0.8）
- Content-Type 必须 `image/` 前缀
- 扩展名白名单：`.jpg/.jpeg/.png/.gif/.webp`（禁 svg 防 XSS）
- **magic bytes 校验**：JPEG `FF D8 FF` / PNG `89 50 4E 47` / GIF `47 49 46 38` / WebP `RIFF...WEBP`
- UUID 重命名，二次校验最终路径在 UPLOAD_DIR 内（防路径遍历）
- 返回 URL：`/uploads/xxx.jpg?v={mtime}`（mtime 版本号便于缓存失效）

## 4. API 端点全览（28 个 Controller）

### 4.1 认证 / 登录

#### AuthController — `/api/auth`
- `POST /api/auth/logout` — 注销：取 token 加入黑名单，清除 Cookie（白名单接口）。**注意**：此处自实现 `extractToken` 顺序为 **Cookie 优先、Authorization 兜底**，与全局 `TokenExtractor`（Authorization 优先、Cookie 兜底）相反，属已知差异

#### EmployeeAuthController — `/api/employee`
- `POST /api/employee/login` — 卡号 + 密码 + storeId 登录（卡号跨店可重复，必须指定门店）；限流 key=cardNo
- `POST /api/employee/phone-login` — 手机号 + 密码登录（phone 全局唯一，自动定位门店）；限流 key=`phone:{phone}`
- `PUT /api/employee/change-password` — 员工改密：校验原密码，新密码至少 8 位
- `GET /api/employee/my-qrcode` — 获取身份二维码（HMAC-SHA256 签名，7 天有效）

#### AdminController — `/api/admin`
- `POST /api/admin/login` — 管理员账号密码登录；成功后写 `auth_token` Cookie
- `POST /api/admin` — 创建管理员（仅超管）
- `PUT /api/admin/{id}` — 修改管理员（**当前 Controller 层调用 `checkSuperAdmin()` 阻止门店管理员访问，仅允许超管**；待修复：Service 层已实现"门店管理员仅能改本店非超管"的逻辑，但被 Controller 拦截成为死代码）
- `PUT /api/admin/{id}/password` — 改密码（本人或超管，改自己的需校验旧密码）
- `DELETE /api/admin/{id}` — 删除管理员（仅超管；不可删除自己）
- `GET /api/admin` — 列出 status=1 管理员（仅超管）

#### TerminalController — `/api/terminal`
- `POST /api/terminal/bind` — 终端绑定：管理员账号密码 + 食堂安全码 双重校验 → 签发 role=3 终端 token（storeId 锁定）；限流 key=`terminal:{username}`
- `GET /api/terminal/refresh` — 滚动续期：用当前终端 token 换新 token（默认 30 天），新 token 的 storeId/storeName/deviceLabel 与原 token 保持一致
- `GET /api/terminal/employees` — 终端本店员工精简列表（仅 id/cardNo/name，不含 phone 等 PII）
- `GET /api/terminal/employee/{cardNo}` — 终端刷卡识别员工（不签发员工 token，storeId 已锁定）

> **待清理**：TerminalController 代码中残留 `System.out.println` 调试语句，待移除。

#### StoreController — `/api/store`
- `GET /api/store` — 全部门店（管理员以上；含 securityCode 敏感字段）
- `GET /api/store/public-list` — 公开列表（免 token；只暴露 id/name/code/address/品牌字段）
- `GET /api/store/{id}` — 门店详情（管理员以上）
- `GET /api/store/{id}/branding` — 公开品牌信息（免 token；ETag 基于 updatedAt，304 零带宽；Cache-Control 5 分钟）
- `PUT /api/store/{id}/branding` — 更新品牌（仅超管；URL 必须 `/uploads/` 开头）
- `GET /api/store/current` — 当前管理食堂（超管 storeId=0 表示全局视图）
- `POST /api/store/{id}/switch` — 超管切换管理食堂（重签 JWT，role 保持 1，storeId 锁定；0=全局）
- `POST /api/store` — 创建门店（超管；自动生成 8 位安全码，排除易混淆字符 0/O/1/I/l）
- `PUT /api/store/{id}` — 修改门店（超管；不允许通过此接口改 securityCode）
- `DELETE /api/store/{id}` — 删除门店（超管）
- `POST /api/store/{id}/reset-security-code` — 重置安全码（超管；重置后旧终端需重新绑定）

#### RechargeRecordController — `/api/recharge`
- `POST /api/recharge` — 充值（role!=0 且 role!=3，即排除员工/终端）
- `GET /api/recharge/store/{storeId}` — 门店充值记录分页（支持日期段）

## 6. 关键业务规则

### 6.1 订单创建（OrderService.createOrder）

**时区**：Asia/Shanghai

校验顺序：
1. 防御性校验：employeeId/storeId/mealType/items 非空
2. **员工只能为自己下单**：`SecurityContext.isEmployee()` 时校验 `currentEmployeeId == dto.employeeId`
3. 多租户：`checkStoreAccess(storeId)`
4. **订单来源 orderSource 处理**：
   - `NORMAL(0)`：正常订餐，走截止时间 + 防重复校验
   - `UNSOLICITED(1)`：未订餐用餐（现场加餐），**绕过**截止时间和防重复校验，允许同一餐次多次下单
5. **次日订单截止校验**：从 `sys_config` 读取 `order_deadline_time`（默认 15:00），订单日期次日前一天 15:00 之后不可下单
6. 员工归属校验：`employee.storeId == order.storeId`
7. **防重复下单**：`selectByEmployeeDateMeal(employeeId, date, mealType)`，已存在则抛"今日该餐次已下单"（UNSOLICITED 绕过）
8. 菜品校验：`selectBatchIds` 批量查询避免 N+1；菜品不存在抛异常（不静默跳过）；菜品归属门店校验；单次限购 `maxPerOrder` 校验
9. **余额原子扣减**：`employeeMapper.deductBalance(employeeId, totalAmount)`，返回 0 表示余额不足
10. 生成订单号：`ORD` + UUID 前 12 位大写
11. 生成取餐码：6 位 `SecureRandom`（防暴力枚举 + 防可预测）

### 6.2 订单完成 / 取消 / 核销

- **completeOrder**：原子状态更新 `WHERE id=? AND status=1 → 2`（防并发重复操作）
- **cancelOrder**：
  1. 状态校验（仅 status=1 可取消）
  2. 次日订单取消截止校验：`cancel_deadline_time`（默认 15:00）
  3. 预检员工账户有效（软删除 selectById 返回 null → 抛"员工账户已失效"）
  4. 原子状态更新（1→3），失败抛"订单状态已变更"
  5. 退款 `addBalance`，失败则事务回滚，订单状态恢复 1
- **pickup（取餐码核销）**：限流 key=`pickup:{storeId}`；按 pickupCode 查订单；状态校验；原子更新 1→2

### 6.3 菜单加载（MenuService）— 缓存策略

**缓存键**：
- `menu:store:{storeId}:date:{date}` — TTL 10 分钟
- `menu:store:{storeId}:year:{y}:month:{m}` — TTL 1 小时

**容错策略**：
- Redis 不可用（dev 环境）自动降级为直查 DB，不影响业务
- `ObjectProvider<RedisTemplate>` 注入，避免 Redis 缺失时启动失败
- 写操作（createMenu/copyMenu/deleteMenu）主动失效缓存 + SSE 广播 `broadcastMenuChanged`
- **菜单加载失败不缓存空数组**：真正的失败（SQL 异常、Redis 异常）向上传播，不进入 cachePut 分支

### 6.4 备份 / 恢复（BackupService + RestoreService）

**格式**：JSON + GZIP（`.json.gz`），兼容 H2 和 MySQL，不依赖外部 mysqldump 命令

**权限模型**：
- 全库备份/恢复：仅超管
- 门店备份/恢复：门店管理员仅限本店；超管可操作任意门店
- 文件名：`full_YYYYMMDD_HHmmss.json.gz` / `store{id}_YYYYMMDD_HHmmss.json.gz`

**Restore 流程（@Transactional）**：
1. 加载并校验备份文件（文件名白名单 / 路径穿越防护 / GZIP 读取）
2. 权限校验：full 仅超管；store 仅本店
3. **恢复前自动快照**：`pre_restore_<type><storeId>_<yyyyMMdd_HHmmss>.json.gz`（便于回滚）
4. 删除目标范围数据：
   - full：`deleteAllBusinessData()` 按 `BackupConstants.DELETE_ORDER` 顺序
   - store：`deleteStoreData(storeId)` — 子表先删（`order_item` JOIN `order`、`menu_item` JOIN `menu`），最后主表；**store 表本身不删**
5. 按 `BackupConstants.TABLES_IN_ORDER` 顺序插入（保留原始 id）
6. **门店备份恢复时跳过 store 表插入**（避免主键冲突）
7. **防提权**：恢复 admin 表时，门店管理员（role>=2）不能创建比自己角色更高的账号（role < callerRole 则 clamp 到 callerRole）
8. **恢复后只读校验**：对每个表 `COUNT(*)` 应与备份声明一致，不一致抛异常触发事务回滚
9. **清理 Redis 缓存**：`evictCache(storeId)`，**当前使用 KEYS 命令**（`redisTemplate.keys(pattern)`）删除 `dish:store:{storeId}:*` 和 `menu:store:{storeId}:*`（全库恢复清理所有门店）；待优化为 SCAN 游标迭代以避免阻塞 Redis
10. **事务边界**：`RestoreService` 独立 Bean 承载 `@Transactional restoreBackup` 方法，通过 Spring 代理让事务生效（避免自调用 AOP 失效）

### 6.5 日终对账流程

#### DailyClose（一次性确认）
- `summary(storeId, date)`：统计订单数/营业额/退款/充值/新增员工/菜品销量 TOP5（基于 status=2 已完成订单）
- `confirm(storeId, date, operatorId)`：防重复（该日期已对账则报错），落库 `daily_close` 表

#### DailySettlement（三阶段状态机）
状态：1=待对账 → 2=已对账 → 3=已关店

- `generateSettlement(storeId, date)`：生成/刷新对账数据（仅 status=1 可刷新，>=2 禁止）
- `confirmSettlement(id)`：1→2，记录 settledAt
- `closeStore(id)`：2→3，记录 closedAt，**需先确认对账才能关店**

**营业额口径**：
- 营业额 = 已完成订单（status=2）totalAmount 之和
- 退款 = 已取消订单（status=3）totalAmount 之和
- 消费总额 = 营业额（同口径）
- 充值无支付方式字段，现金充值 = 充值总额，线上充值 = 0（预留扩展）

### 6.6 报表类型（ReportService）

统一鉴权：`checkReportAccess(storeId)` = `checkStoreAccess` + `canViewFinance`（role=1/2/4/6）

| 报表 | 端点 | 说明 |

## 7. Redis 缓存键模式

### 7.1 业务缓存键

| 键模式 | 用途 | TTL | 失效策略 |
|--------|------|-----|----------|
| `dish:store:{storeId}:list` | 门店在售菜品列表（status=1） | 30 分钟 | 写操作主动 `cacheEvictByStore` |
| `dish:store:{storeId}:list:all` | 门店全量菜品（含已下架，终端缓存） | 30 分钟 | **当前未清除（已知 bug，待修复）**：`cacheEvictByStore` 实际仅清 `list` 和 `new`，漏清 `:all` |
| `dish:store:{storeId}:new` | 门店新品列表 | 30 分钟 | 同上 |
| `menu:store:{storeId}:date:{date}` | 指定日期菜单 | 10 分钟 | createMenu/copyMenu/deleteMenu 主动失效 |
| `menu:store:{storeId}:year:{year}:month:{month}` | 月历已配置日期 | 1 小时 | 同上 |

### 7.2 缓存失效策略（RestoreService.evictCache）

- 恢复备份后调用，避免前端读到旧数据
- **门店级清理**：`KEYS dish:store:{storeId}:*` + `KEYS menu:store:{storeId}:*`
- **全库清理**：`KEYS dish:store:*` + `KEYS menu:store:*`
- **当前使用 KEYS 命令（待优化为 SCAN）**：代码实际调用 `redisTemplate.keys(pattern)`，即 KEYS 命令；生产环境大 keyspace 下可能阻塞 Redis，应改为 SCAN 游标迭代
- 失败不影响恢复结果（缓存有 TTL，会自然过期）

### 7.3 非 Redis 的内存缓存

- **SSE ticket**（SseTicketService）：`ConcurrentHashMap<String, TicketEntry>`，32 字节 hex，30 秒过期，一次性消费，懒清理
- **登录限流**（LoginRateLimiter）：`ConcurrentHashMap<String, FailInfo>`，单实例
- **SSE 连接**（SseService）：`Map<Long, Set<SseEmitter>>` 按 storeId 维度管理终端长连接，默认 30 分钟超时，25 秒心跳

### 7.4 Redis 容错

- dev 环境完全禁用 Redis（`application-dev.yml` 排除 `RedisAutoConfiguration`）
- 服务层使用 `ObjectProvider<RedisTemplate>` 注入，Redis 不可用时降级为直查 DB
- 所有 Redis 读写操作 try-catch 后只记录日志，不抛异常

## 8. SSE 实时推送

### 8.1 认证流程（一次性 ticket）

为避免 token 通过 URL query 泄漏（进入浏览器历史/Referer/代理日志），SSE 采用一次性 ticket 机制：

```
1. 终端用 Bearer token 调 GET /api/sse/ticket → 获得 30s 一次性 ticket
2. 终端用 ticket 建立 EventSource: GET /api/sse/subscribe?ticket=xxx
3. 后端校验 ticket（30s 有效，一次性消费，懒清理）→ 建立长连接
4. 连接建立后 ticket 立即销毁
```

### 8.2 推送事件

- `dish_changed`：菜品变更（create/update/delete/toggle/batch）
- `dish_batch_changed`：批量菜品变更
- `menu_changed`：菜单变更（含日期信息，终端精确失效指定日期菜单缓存）

### 8.3 连接管理

- 按 storeId 维度管理：`Map<Long, Set<SseEmitter>>`
- 默认 30 分钟超时
- 25 秒心跳保活

- **全局 multipart 限制**：`spring.servlet.multipart.max-request-size=1GB` / `max-file-size=1GB`（用于备份导入 `BackupController.import`，单文件备份可达数百 MB）；图片上传端点另有 5MB 业务上限

## 11. 其他系统级约定

### 11.1 全局异常处理
- `GlobalExceptionHandler` 统一异常转换（SecurityException → 403/401，BusinessException → 400，其他 → 500）
- `UnauthorizedResponseWriter` 写 401 响应（支持 AJAX `X-Requested-With: XMLHttpRequest` 判断，返回 JSON 而非重定向）

### 11.2 操作日志（OperationLogAspect）
- `@OperationLog` 注解 + AOP 切面，记录管理员操作到 `sys_operation_log`
- 字段：adminId, adminName, storeId, operation, method, params, ip, status, errorMsg
- 门店管理员仅看本店日志

### 11.3 优雅停机
- `server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 30s`
- `GracefulShutdownHandler` + `ShutdownLifecycleHook`：接收 SIGTERM 后新请求返回 503，正在处理的请求继续完成

### 11.4 通知调度
- 通知 `publishAt` 到点自动上架，`expireAt` 到点自动下架（status=0）
- 调度器定期扫描并更新状态

### 11.5 安全响应头（SecurityHeadersFilter）

由 `SecurityHeadersFilter` 统一设置以下响应头：

| 响应头 | 值 | 说明 |
|--------|------|------|
| `X-Frame-Options` | `DENY` | 防点击劫持 |
| `X-Content-Type-Options` | `nosniff` | 防 MIME 嗅探 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 控制 Referer 泄露 |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` | 禁用摄像头/麦克风/地理定位 |
| `X-Powered-By` | （空字符串） | 移除框架指纹 |
| `Cache-Control` | `no-cache, no-store, must-revalidate` | 防敏感接口响应被缓存 |

> **CSP 与 HSTS 不在此 Filter 设置**：代码注释明确"由 nginx 在前端响应中添加更合适"，因此 `Content-Security-Policy` 和 `Strict-Transport-Security` 由 nginx 负责（后端响应经 nginx 反代时统一注入）。

## 12. 安全边界总结

| 边界 | 策略 |
|------|------|
| token 存储 | HttpOnly Cookie（前端不可读）+ SameSite=Strict |
| token 提取 | Authorization Bearer 优先，Cookie 兜底；禁止 URL query |
| SSE 认证 | 一次性 ticket（30s，一次性消费） |
| 门店隔离 | StoreAccessInterceptor + SecurityContext.checkStoreAccess（fail-closed） |
| 登录限流 | 10 次失败锁定 5 分钟（内网放宽） |
| 密码 | BCrypt + 最小 8 位 + passwordUpdatedAt 新鲜度校验 |
| token 失效 | 黑名单（DB 持久化）+ 软删除/禁用即失效 |
| 文件上传 | 5MB + magic bytes + 扩展名白名单 + UUID 重命名 + 路径遍历防护 |
| CSV 导出 | UTF-8 BOM + 防公式注入 |
| 取餐码 | 6 位 SecureRandom + 限流防暴力枚举 |
| 二维码签名 | HMAC-SHA256 + 常量时间比较防时序攻击 |
| CORS | 白名单 origin + OPTIONS 放行 |
| 安全头 | SecurityHeadersFilter 设置 X-Frame-Options/X-Content-Type-Options/Referrer-Policy/Permissions-Policy/X-Powered-By/Cache-Control（详见 §11.5）；**CSP 与 HSTS 由 nginx 负责** |
