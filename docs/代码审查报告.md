# 企业食堂项目完整代码审查报告

**审查方式**：4 个不同身份子代理并行只读审查（安全审计师 / 后端架构审查员 / 前端代码质量审查员 / X86 终端审查员），未修改任何文件。
**审查范围**：backend（Spring Boot + MyBatis-Plus + JWT + MySQL + Redis）、admin-web（Vue3 + TS）、h5（Vue3 + TS）、terminal（Vue3）+ src-python（PyQt5 外壳）、部署配置（docker-compose / nginx）。
**审查日期**：2026-08-14

> **修复状态**：本报告所列问题已于 2026-08-15 完成一轮集中修复（全部高危 + 绝大部分中危 + 两项新需求），逐项修复状态、部署注意事项与遗留事项见 [修复执行记录.md](./修复执行记录.md)。

## 总体结论

项目纵深防御基础扎实，以下维度均已覆盖且表现良好：

- SQL 注入：全部 MyBatis-Plus 参数化 + JdbcTemplate `?` 占位符，无字符串拼接
- JWT 密钥：生产强制 ≥32 字节、禁用默认/弱密钥黑名单，缺失即拒绝启动
- 口令：BCrypt（strength=10）、复杂度校验、改密后旧 token 失效
- 会话：HttpOnly Cookie + SameSite、token 黑名单、滑动续期、登录限流（10 次/锁 5 分钟）
- CSRF：SameSite=Strict + Origin 校验 + SSE 一次性 ticket（30s）
- 传输：后端仅绑 127.0.0.1（18082）、nginx 全量 HSTS/CSP/nosniff/X-Frame-Options
- 文件上传：UUID 重命名 + 路径穿越防护 + magic bytes 校验 + 禁止 svg
- 图片鉴权：HMAC 签名 URL（128bit）+ 过期时间
- 越权/多租户：门店隔离拦截器 + 备份按门店权限校验
- 前端：401 并发去重、SSE 重连退避、定时器/事件清理、图片懒加载、防布局抖动

**未发现可直接未授权 RCE 或 SQL 注入的"严重"级问题。** 主要风险集中在：

1. **X86 终端本地链路**：token 生命周期/明文存储、本地服务鉴权、升级包完整性
2. **生产配置项**：CORS 默认 `*`、备份导入无限制
3. **并发竞态**：订单防重、结算、采购入库
4. **对账口径不一致**：双套对账模块并存、订餐日期 vs 下单时间
5. **前端打包体积**：全量 echarts/element-plus/图标、无分包
6. **大量重复代码**：date.ts、imageSign.ts、金额格式化、对账逻辑、桥接契约

## 一、安全类问题

### 高（5 项）

| # | 组件 | 位置 | 问题 | 建议 |
|---|---|---|---|---|
| H1 | backend / terminal | `backend/.../security/JwtTokenProvider.java`、`terminal/src/api/index.ts` | 终端 token 有效期 365 天且明文存 localStorage，泄露后一年内可无限以门店身份下单/取餐/查询 | 缩至 30 天内（已有 `refreshTerminalToken` 支持滚动续期）；改 DPAPI 加密存储 |
| H2 | src-python | `src-python/server.py`、`src-python/bridge.py` | 本地服务 Origin 用 `startswith('http://127.0.0.1:')` 弱校验且空 Origin/Referer 直接放行；`set_config`/`quit`/`restart_card_reader` 等状态变更无鉴权可被本机任意来源 CSRF | 改为 host+port 全等比较、校验 Host 头、状态变更加一次性本地令牌 |
| H3 | src-python | `src-python/updater.py` | 升级包下载后无 SHA256/签名校验即 `/VERYSILENT` 静默执行，`update_check_url` 可配置 → 潜在 RCE | 限定可信域名、校验哈希/Authenticode 签名后再执行 |
| H4 | backend | `backend/.../config/WebConfig.java` | CORS 未配置 `CORS_ALLOWED_ORIGINS` 时默认 `allowedOriginPatterns("*")` + `allowCredentials(true)` | 生产强制配置精确白名单并启动校验非空，废弃 `*`+credentials 兜底 |
| H5 | backend | `backend/.../service/BackupService.java`、`controller/BackupController.java` | 备份导入 1GB 上限 + `readAllBytes()` 无上限 + GZIP 无限制解压 → 压缩炸弹 DoS；与 nginx `client_max_body_size 50m` 不一致 | 设导入大小上限、限制解压后大小、流式读取 |

### 中（5 项）

| # | 组件 | 位置 | 问题 |
|---|---|---|---|
| M1 | src-python | `src-python/bridge.py` | `eval_js` 后门仅靠 `CANTEEN_DEBUG` 环境变量门控，生产构建未剥离 |
| M2 | backend | `backend/.../service/WechatMessageService.java` | 微信回调 XML 仅禁用外部实体引用，未禁 DTD/内部实体（Billion Laughs）、未限请求体大小 |
| M3 | backend / h5 | `backend/.../security/JwtTokenProvider.java` | 员工 token 30 天 + 滑动续期实现"永不失效"，且余额写死在 token 中不落库比对、无法单独吊销 |
| M4 | docker-compose | `docker-compose.yml` | `INIT_ADMIN_USERNAME/PASSWORD` 未配置时默认 admin/123456 超管弱口令 |
| M5 | backend / src-python | `FileController.java`、`BackupService.java`、`src-python/server.py` | 错误信息回显堆栈/内部路径给客户端，辅助探测服务器细节 |

### 低 / 提示（8 项）

- **L1** 文件上传依赖客户端 Content-Type（已有 magic bytes 兜底）— FileController.java
- **L2** H5 员工信息（余额/卡号）明文存 localStorage — h5/src/stores/auth.ts
- **L3** admin-web nginx CSP `style-src 'unsafe-inline'` + `connect-src` 含遗留的本地 8765 调试端口 — nginx.conf
- **L4** 终端配置文件与 token 无 ACL，本机任意用户可读 — src-python/config.py、terminal/src/api/index.ts
- **L5** 上传/导入接口无频率与总量限制 — FileController、BackupController
- **I1** 开发环境 Redis 无密码（生产已加固）
- **I2** 微信回调明文模式、无防重放、未限制来源 IP
- **I3** h5 依赖含 vconsole 调试组件，需确认未打入生产

## 二、后端功能 / 冗余 / 效率问题

### 高（3 项）

1. **订单防重复下单并发竞态**：`OrderService.java` 先查后扣款后插入，`order` 表无 `(employee_id,date,meal_type)` 唯一约束（V23 还删了取餐码唯一索引）→ 并发可重复下单扣款。
2. **双套日终对账模块并存**：`DailyCloseService`（/api/daily-close）与 `DailySettlementService`（/api/settlement）两张表两套汇总，财务口径易漂移。
3. **看板与报表"今日营业额"口径不一致**：看板按 `order.date`（订餐日期）、对账/报表按 `created_at`（下单时间），次日订餐场景对不上账。

### 中（11 项）

4. **采购入库库存累加非原子**：`PurchaseService.java` 先查后改，并发可重复累加/丢失更新 → 应改原子 `UPDATE stock_qty = stock_qty + ?`。
5. **充值接口无幂等**：RechargeRecordService 重复提交会重复加余额。
6. **结算生成/确认/关店无并发锁**：DailySettlementService 并发抛 DuplicateKey 变 500，状态流转无乐观锁。
7. **团体订单状态流转非原子**：GroupOrderService confirm/cancel/complete 均为 selectById 后直接 updateById，无 `WHERE status=?` 条件。
8. **定时任务无分布式锁**：BackupSchedulerService / OrderStatusScheduler / NotificationService 自动下架，多实例会重复执行；备份失败仅 `log.warn` 静默吞掉。
9. **`markExpiredOrdersAsMissed` 无匹配索引**：`OrderService.java` 查询条件 `status+date` 无法命中现有 `(store_id,date,status)` 索引前缀。
10. **备份导入全量 `readAllBytes()` 入内存**：OOM 风险。
11. **报表/对账全内存聚合**：ReportService/DailyClose/DailySettlement 月报、同比把整段订单 `SELECT *` 进 JVM 再 stream 过滤，无下推 SQL。
12. **回收站/全量菜品内存手工分页**：DishService `getTrashList` 全量查后 subList。
13. **微信 HTTP 无超时**：WechatNotifyService/WechatAuthService `new RestTemplate()` 未配超时，微信接口挂起时线程无限期阻塞。
14. **RestoreService 快照失败被忽略** + 恢复在单事务内 DELETE+INSERT 全量表长持锁。

### 低 / 提示（12 项）

- 批量导入按姓名匹配员工存在同名误匹配（EmployeeService.selectByNameAndStore）
- `getDeadlineTime` 双重 `catch(Exception ignored)` 静默吞异常回退默认 15:00
- 日终对账逻辑三处重复（ReportService/DailyCloseService/DailySettlementService）
- `currentOperatorName` 重复、批量填充关联名称模式三处重复
- Controller 鉴权写法分散手动重复，易漏写
- 魔法数字 2/3/4 未统一用 OrderStatus 枚举
- 时区硬编码 `Asia/Shanghai` 与配置重复
- 缓存无防穿透/击穿（DishService/MenuService 空结果不缓存）
- 微信订阅消息逐员工串行发送；看板 7 天趋势全量加载后多次 stream
- OperationLogAspect 同步写日志拖慢业务线程
- WechatAuthService bindToken 缓存无上限懒清理
- 共享 `DocumentBuilderFactory` 并发解析线程不安全
- `BusinessException.code` 直接映射 HTTP 状态码语义混乱（code=2001 会回退 400）

## 三、前端（admin-web / h5）问题

### 高（1 项）

1. **admin-web 打包体积过大**：`main.ts` 全量 `app.use(ElementPlus)` + 遍历注册全部图标 + `import * as echarts` 全量 + xlsx 全量，且 vite.config.ts 无 manualChunks 分包 → 首屏加载慢。

### 中（8 项）

2. **admin-web 无权限访问强制登出**：`router/index.ts` 角色不匹配时 `clearState()` 踢出登录，与 API 层 403"仅提示不踢出"行为不一致，敲 URL 即掉线。
3. **两端 date.ts 重复且实现有差异**：admin-web 与 h5 核心函数一致但写法/能力集合不同（admin-web 用 pad2、h5 用 padStart，各自独有函数），极易实现漂移 → 正是用户关注的日期不一致隐患。
4. **imageSign.ts 逐字重复**（admin-web 与 h5 完全一致，复制粘贴式复用，改一处漏一处）。
5. **金额格式化重复且风格不一致**：admin-web `utils/money.ts`（含 `¥`）vs h5 `useFormat.ts`（模板拼 `¥`）。
6. **Dashboard 切换门店未先 dispose 再 init echarts**：Dashboard.vue。
7. **h5 vant 全量引入**（main.ts 注释已自认待优化）。
8. **h5 历史订单 `as any` 兼容旧字段**（Order.vue 5 处）。
9. **模板内调用方法每次渲染重算**：Layout.vue、DishManagement.vue、MenuManagement.vue、h5 Order.vue → 应提升为 computed/预生成 Map。

### 低 / 提示（8 项）

- admin-web `utils/permission.ts` 疑似死代码（hasPermission/canAccessStore 无任何引用）
- h5 `@vueuse/core` 未使用依赖
- h5 内部两套日期函数（`useFormat.formatDate` vs `utils/date.formatDateStr`）重叠
- h5 `useOrderConfig` 用 `as any` 绕过拦截器解包类型
- 版本检测两端重复且 key/刷新策略不一致
- 图片签名失败降级后 URL 未签名 → 403 图片不显示，无重试；批量签名按数组下标对齐，后端乱序会签错图
- 部分列表页/看板缺"加载失败重试"错误态

**正向确认**：401 并发去重、SSE 生命周期与重连退避、定时器/事件监听清理、图片懒加载与压缩、h5 全量加载防布局抖动等均已落实。

## 四、X86 终端（terminal + src-python）问题

### 高（1 项）

1. **员工头像双重缓存冗余**：`employeeCache.ts` `preloadAvatars` 全量预载写入 `images` store，但渲染链路从不读取（走独立的 `getCachedAvatar` 懒加载）→ 同一头像下载两次、存储两份，且 `dbClearUnusedImages` 每次菜品刷新全游标扫描这份死数据。

### 中（6 项）

2. **watchdog 与"退出应用"冲突**：`watchdog.py` 无法区分正常退出与崩溃，退出后 10~25 秒被自动拉起，生产环境"退出"形同虚设。
3. **`set_config` 缺枚举/范围校验**：bridge.py 只校验 `str` 类型，坏值写入 config.json 后静默失效。
4. **`card_interval` 在 HID 回退模式下不生效**：card_reader.py 与 card_helper.py 两套防抖体系，前端键盘缓冲固定 80ms。
5. **菜品变更全量重写 + 全量图片游标扫描**：`cache.ts` 每次 dish_changed 全量 `dbClearDishesByStore`+`dbPutDishes` 再全量扫描 images store。
6. **SSE 降级后双通道重复请求**：每 5 分钟低频重启 SSE 与兜底轮询同时运行，叠加全量刷新。
7. **文档与实现严重漂移**：04-X86终端.md / 05-PythonShell.md 多处与实际不符（端口 15118、持久化路径 `%APPDATA%`、默认 server_url、ACAO/方法校验现状、OrderQuery 已修复、头像缓存策略）。

### 低 / 提示（10 项）

- `useCardReader` 键盘缓冲不过滤非数字，误敲字母触发无效查询
- `useDevicePresence` 注释与实现矛盾（浏览器环境 `hasCardReader=false`）
- ERROR_CODES 与 `parse_card_number` 在 card_reader.py / card_helper.py 重复实现
- `check_card_reader` 直接访问读卡器私有属性 `_thread/_running/_dll`
- 版本号多处硬编码（updater.py CURRENT_VERSION vs VERSIONS.json vs installer.iss）易漂移
- 员工缓存网络未命中不回写 IndexedDB（新员工每次刷卡重复走网络）
- HID 模式 `status_info` 同步阻塞最多 3 秒、`/status`/`/beep` CORS 全开无鉴权
- `GET /__api__/config` 无鉴权暴露完整配置
- `window.__onCardRead` 可被页面任意脚本伪造刷卡（建议校验 `^\d{4,16}$`）
- 启动时 glob 删除持久化锁文件有误删风险
- `server_url` 无 `http(s)://` 格式校验
